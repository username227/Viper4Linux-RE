# Android–Linux DSP Validation

This document records direct comparisons between **ViPER4Linux-RE** on Arch Linux and the installed **ViPER4Android-RE** audio driver on Android. The objective is to check that each effect behaves as intended, identify discrepancies, and improve the Linux implementation where justified. **A matching output is evidence of parity, not proof that either implementation is inherently better.**

Both test programs create *isolated* DSP instances. They do not alter active playback settings or audio routing.

### Test procedure used and standards for future tests

1. Create a deterministic common input and run isolated Android and Linux DSP instances with the **same sample rate, format, effect controls and processing block size**. Use the real Android native driver and Linux LADSPA adapter, not a GUI-slider-only check.
2. Record an effect-OFF baseline and expected limiter lookahead (256 stereo frames at 48 kHz). Compare baseline, complete effect-ON capture, time windows during startup/anti-pop and after settling, and the effect delta (ON minus OFF).
3. Report both exact float32 sample count and RMS/max/normalized differences; any numerical error must be described precisely. A difference consistent with floating-point rounding is **not evidence of an audible problem**, nor proof of its precise CPU/compiler cause.
4. Include independent correctness checks: left-only/right-only channel isolation, expected latency and buffering with additional block sizes, changes between modes and audio continuity where relevant. Two platforms can share the same bug and still yield matching output.
5. Keep temporary CMake/mock-IPC tests away from the installed audio backend, user profiles, system PipeWire routing and pinned submodule. Never present a temporary test-only source patch as a committed production change.
6. Log exact commands, references, output metrics, test limitations, repository commits/PRs and whether dependencies or packaging changed. Require maintainer review before merging, changing a DSP pin, releasing or updating AUR.

## ViPER Bass: Natural — November 10, 2026

**Test setup.** The installed Android driver and the Linux LADSPA adapter both processed exactly the same test audio: 16,384 stereo frames (32,768 float32 samples), at 48 kHz, in 512-frame blocks. The settings were Natural Bass mode, 65 Hz, gain 3.0, with anti-pop enabled. Limiter threshold was 0.5; other enhancements were off. Both systems used the pinned ViPERDSP revision `6fc1f1b8`.

**Baseline.** With Bass off, Android returned the original audio unchanged apart from ViPERDSP's expected 256-frame (5.33 ms) limiter delay. The Linux and Android outputs matched **32,768 out of 32,768 samples**, exactly.

**First Bass-on comparison.** The outputs were close but not identical: the full-capture RMS difference was about 0.00008737 and maximum absolute difference about 0.00042275. Investigation showed that Linux initially enabled Bass using a temporary gain of 10, then switched to the actual gain of 3. ViPERDSP smooths such a change, so the two systems began processing from different internal states. The error decreased over the course of the capture.

**Correction.** The Linux adapter now prepares the selected Bass parameters while Bass is disabled, then enables the effect. This preserves normal smoothing for changes during playback. The correction is in `src/backend/processor.inc`, introduced on the Bass validation branch in commit `78825b6`.

**Rerun against the committed correction.** The test rebuilt the actual Linux LADSPA adapter from commit `78825b6` and compared it against the same Android reference:

## ViPER Bass: Pure Bass+ — November 10, 2026

**Test setup.** We compared the actual Android driver with the isolated Linux LADSPA adapter from the Bass validation branch, using Pure Bass+ (mode 1), 65 Hz, gain 3.0, anti-pop enabled, 48 kHz stereo float32, and 512-frame blocks. The longer test processed 131,072 frames (2.73 seconds), including the period after the one-second anti-pop ramp.

**Results.** With Bass off, all **262,144 audio samples matched exactly**. With Pure Bass+ enabled, the RMS difference between Android and Linux was just **2.70×10⁻⁹**, and the largest difference was **1.49×10⁻⁸**. About 55.6% of samples matched bit-for-bit; the remainder differed by tiny amounts consistent with floating-point rounding. This very small difference persisted across the recording, without an accumulating or startup-dependent error. We cannot prove the exact numerical cause from these measurements alone. **No Linux integration correction is justified by this discrepancy.**

**Independent stereo-channel audit.** We fed audio into the left channel only and kept the right channel completely silent. With Bass off, both drivers preserved silence in the right channel. With the original Pure Bass+ code, **both Android and Linux** generated unintended audio in the right channel: 129,760 of 131,072 right-channel samples became nonzero. After the first second, that unwanted right-channel RMS was **66.57%** of the left-channel RMS. The original Android and Linux outputs remained nearly identical (max difference 1.49×10⁻⁸; RMS difference 2.34×10⁻⁹).

**Root cause and isolated experiment.** Upstream Pure Bass+ obtains a stereo `WaveBuffer` offset expressed in **frames**, then mistakenly uses it as an offset into **interleaved float samples**. We corrected the two left/right buffer write indices in a **private, temporary Linux DSP build copy** by multiplying the frame position by two. The result: **zero nonzero samples on the silent right channel, zero right-channel RMS and peak**, both over the full 2.73-second capture and after one second. The effect-off output remained completely unchanged. As expected, the corrected Bass-on output no longer matches the uncorrected Android reference.

**Status.** This is a demonstrated shared upstream correctness defect, not a Linux-integration parity failure. The two-line correction has been committed to a dedicated branch in the user’s temporary upstream fork: [`username227/ViPERDSP@64ecd00`](https://github.com/username227/ViPERDSP/commit/64ecd00cf737b8e83fb080fda5584572038c50c1), branch `fix/pure-bass-stereo-buffer-offset`. The source diff contains only two indexed stereo-buffer write changes. The upstream pull request was submitted on November 10, 2026: [likelikeslike/ViPERDSP#7](https://github.com/likelikeslike/ViPERDSP/pull/7). It contains one commit changing only two source indexing expressions; the PR is open and awaiting upstream review. The checked-in ViPERDSP submodule, installed DSP, and production configuration remain unchanged. Additional block-size and right-only regression checks would further strengthen coverage.


**Upstream status history — November 11, 2026 (before the dependency integration):** [ViPERDSP PR #7](https://github.com/likelikeslike/ViPERDSP/pull/7) had been **merged** while the validation branch still pinned the earlier DSP revision. The tested correction was therefore not yet part of the then-current Linux build.

**Subsequent dependency integration:** Commit `23465443` merges `deps/viperdsp-pure-bass-stereo-fix` and changes only the submodule gitlink from `6fc1f1b8` to upstream `likelikeslike/ViPERDSP` `f5157363`. The two-line buffer-index fix is now part of the *validation branch's source dependency*. **Original run.** The maintainer ran `python3 ~/Downloads/prepare_viper_psychoacoustic_bass_suite_v2.py --run` against the installed Android native driver and the Linux LADSPA adapter built from local HEAD `c364cdc`, pinned ViPERDSP `6fc1f1b8`. **Original discrepancy.** Order 2 was bit-exact; order 3–5, cutoff, original-level and intensity-100 tests generally showed a meaningful startup discrepancy, followed by exactly matching or effectively near-identical settled audio. E.g. order 3 ON RMS error was `0.0009807192992` and max `0.01466274634` before correction, but its final 1 second matched exactly. **Root-cause evidence.** Native `ViPERDSP/viper/utils/Harmonic.cpp` uses `const float abs_coeff = abs(coeffs[i]);` in `Harmonic::UpdateCoeffs`, where the maximum magnitude controls `biggest_coeff_` / harmonic warm-up length. On Linux GCC/libstdc++ the unqualified call resolves to an integer absolute-value overload, truncating fractional coefficients (e.g. 0.7, 0.5, 0.4) to zero; the 2nd-order unit coefficient is unaffected. The same source built with an explicit floating-point overload, `std::abs(coeffs[i])`, reproduces the existing captured Android PCM. This is **strong experimental confirmation of a platform-sensitive native DSP portability bug**; the exact overload used by the installed Android binary was not independently inspected.

**Private verification.** `python3 ~/Downloads/verify_viper_psycho_harmonic_abs.py` copied the local checkout and dependency into a throwaway source tree; only `abs(coeffs[i])` was replaced with `std::abs(coeffs[i])` in that private native dependency. It rebuilt Linux and reprocessed every case against **the same original Android recordings**, without rerunning the phone. Full ON results:

## Output position 1 — Master OFF true-bypass correction and native regression (November 11, 2026)

Re-enabling Master ramps back to the native DSP and restores output gain, balance and the mandatory peak limiter.
